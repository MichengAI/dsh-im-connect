## 目标

分三部分实现并分别提交：操作菜单、审批与问答按钮、通用文件输入。复用现有准入和命令权限、Host 命令及 Chat 附件契约；不安装正式 Profile、不推送和发布。

## 一、操作菜单

已实现 `/menu`、`/m` 及会话、工作区、模型分页选择、新建、停止、导出、状态、帮助。服务端保存动作，随机 token 绑定账号、聊天、操作者、会话，15 分钟有效，一次性消费；执行重新检查权限。普通文字退出数字菜单，问答优先。

Telegram、飞书/Lark 原生按钮；企业微信不超过 6 项时使用原生卡片，否则文字降级。钉钉、QQ、微信为文字序号菜单；未引入需要额外发布的自有钉钉交互模板。菜单与问答的具体呈现范围以 README 为准。

构建通过，三个兼容版本各 581 项通过、0 失败、0 跳过。原生请求及统一隔离有自动化覆盖，真实渠道卡片渲染、回调权限仍未验证。

关联提交：本次 `feat: add scoped interactive command menus`。

## 二、审批与问答

已接入原生按钮适配渠道；批准一次/拒绝、单选和多选提交复用既有 Host 答案结构。原操作者、会话和具体问题/审批请求身份重新校验；原生按钮失效或无法完整展示时沿用文字提示，不缩减审批参数。工具审批仍仅授权私聊用户可处理；命令关闭不影响已存在的交互。提示和按钮提供中英文。

三版各 583 项通过、0 失败、0 跳过；新增审批身份、旧按钮重放、多选显式提交回归。真实卡片渲染和回调尚未验证。关联提交：本次 `feat: add approval and question action buttons`。

## 三、文件输入

微信、企微、钉钉、飞书/Lark、QQ、Telegram 接收普通文件，保留下载地址校验、加密解密、大小限制和原消息上下文。微信文件直接传递字节，不再将缓存路径注入模型。引擎通过 `fileUploads.uploadStream` 上传，再使用 `sessionController.prompt` 提交 `type: file, receiptId`，不自建文件解析体系。

每条消息最多 4 个普通文件、累计 20 MiB，渠道下载上限可能更低；上传限时 120 秒并传递生命周期信号。文件说明文字不作为命令。文件能否被模型/工具解析与 Chat 一致。

两个 0.1.5 版本支持完整文件上传；0.1.2-rc.1 没有这套 Chat 契约，明确提示升级，不能称为旧版支持文件输入。未新增生产依赖。

三版完整回归各 603 项通过、0 失败、0 跳过。新版使用真实 FileUploads 和 SessionCommandController 验证凭据与最终 file attachment；旧版核对契约缺失与拒绝行为。全部渠道有普通文件接收自动化覆盖；下载错误、超限、说明文字、上传中停用账号有回归。顺带验证飞书原生卡片业务错误能触发文字降级。

关联提交：本次 `feat: accept channel files through Chat upload admission`。未安装正式 Profile、未推送、未发布。
