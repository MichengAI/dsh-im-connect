# 命令级权限扩展

状态：实现中（随功能 PR 更新）
更新时间：2026-11-19（Asia/Shanghai）

## 背景

原有 `commandPermissions` 只有账号级的私聊、群聊命令开关；`CommandScope.users` 虽在数据结构中保留，但 `canExecuteCommand` 实际只读取 `scope.enabled`，因此无法表达“某个用户只能执行哪些命令”。

本扩展在旧结构上增加可选的命令清单和用户例外，同时保持旧配置行为不变。

## 数据模型

```json
{
  "schemaVersion": 2,
  "dm": {
    "enabled": true,
    "defaultAllowedCommands": ["help", "status"],
    "users": [
      { "userId": "u_1001", "enabled": true, "allowedCommands": ["new", "sessions"] },
      { "userId": "u_1002", "enabled": false }
    ]
  },
  "group": {
    "enabled": true,
    "users": []
  }
}
```

- `schemaVersion: 2` 才会启用用户例外和命令清单；旧配置没有该字段时继续按 `enabled` 布尔值执行。
- `defaultAllowedCommands` 省略表示不限制命令；空数组表示不允许任何命令。
- 用户条目 `allowedCommands` 省略表示“跟随默认”：同时继承场景 `enabled` 与 `defaultAllowedCommands`；`["*"]` 表示明确全部命令；空数组表示该用户不能执行命令。
- 用户条目 `enabled: false` 时不能同时配置非空 `allowedCommands`，服务端会拒绝该组合。
- 场景 `enabled: false` 时，“跟随默认”的用户例外仍按关闭处理；只有显式配置了非空命令清单的用户例外才会覆盖该开关。
- 没有 `schemaVersion: 2` 的旧配置不接受 `defaultAllowedCommands` / `allowedCommands`，避免字段被静默忽略造成 fail-open；旧 `users` 条目继续兼容但不启用。

## 命令匹配

从消息第一个 token 提取命令，去掉前导 `/` 后小写，并按以下别名归一化：

`m`→`menu`、`clear`→`new`、`sessionlist`→`sessions`、`workspacelist`→`workspaces`、`current`→`status`、`reasonings`→`reasoninglist`、`presetlist`→`presets`。`/reasoning`（修改推理等级）与 `/reasonings` / `/reasoninglist`（只读列表）使用不同权限 ID。

`/menu <section>` 会按实际业务命令匹配：`sessions`、`workspaces`、`models`、`presets`、`reasoning` 分别归入对应命令权限，只有裸 `/menu` 才按 `menu` 匹配。

Host 扩展命令没有静态白名单限制；只要配置了其命令名即可匹配。

权限粒度是命令名级：允许 `/queue` 会同时允许 `/queue remove`、`/queue edit`、`/queue steer` 等子操作；`/model`、`/preset`、`/workspace`、`/goal` 同理。当前版本不拆分子命令。

## 设置页命令发现

设置页通过只读 `GET /accounts/:id/commands` 合并当前绑定会话的 `commands.list(agent)` 结果，并在没有可用会话或接口失败时回退到内置常用命令。候选只用于输入提示，不参与权限执行；完整跨会话、按 preset 区分的动态目录不在当前版本范围。

## 设置与执行顺序

1. 原有私聊准入/群聊触发规则先执行；
2. 命令进入 Gateway 后读取账号命令权限；
3. `enabled` 与用户例外决定是否允许执行；
4. 命令清单决定具体命令；
5. 通过后才进入 `ChatCommands`。

关闭命令不影响普通对话、附件、审批和问题回答。
